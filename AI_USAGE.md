# AI Usage Audit

This file records meaningful AI-assisted engineering work performed in this repository. Its purpose is to make AI involvement in the codebase **traceable and honest**: what was asked of the AI, what it produced, what was wrong with that output, how the engineer corrected it, and what was ultimately decided.

This is an audit trail, not a changelog. It exists so that anyone reviewing this project can see exactly where AI contributed, where it was wrong, and how the engineer exercised judgment.

## Entry Structure

Every future AI usage entry must follow this structure:

```text
Task
↓
Objective
↓
Prompt
↓
AI First Attempt
↓
Engineer Review
↓
Issues Found
↓
Correction
↓
Validation
↓
Final Decision
```

Each field, explained:

* **Task** — the specific, scoped unit of engineering work.
* **Objective** — what the task was meant to achieve.
* **Prompt** — what was actually given to the AI (context included).
* **AI First Attempt** — the AI's output, preserved as-is, including mistakes.
* **Engineer Review** — the engineer's assessment of that output.
* **Issues Found** — concrete problems identified, if any.
* **Correction** — what the engineer changed, and why.
* **Validation** — how the corrected output was actually verified (tests run, checks performed). If nothing was actually validated, this must say so.
* **Final Decision** — ACCEPT / MODIFY / REJECT, with brief reasoning.

## Rules

1. **Preserve incorrect AI first attempts.** Do not delete or clean up a flawed first attempt — record it as it was produced.
2. **Do not rewrite AI history.** Entries are not edited after the fact to look better in hindsight.
3. **Record engineer decisions.** Every entry states what the engineer decided and why.
4. **Record corrections.** If the engineer changed the AI's output, the change and its reasoning are documented.
5. **Never claim validation that was not actually performed.** If tests weren't run, say tests weren't run. If coverage wasn't measured, say so.
6. **Explicitly flag uncertainty.** If the engineer or the AI is not confident about something, that uncertainty is recorded, not hidden.
7. **AI-generated output is not automatically accepted.** Every entry ends in an explicit ACCEPT, MODIFY, or REJECT decision.

  - A `MODIFY` decision on an AI run does not itself change the task's own Phase-4 `status`/`review_status` — reviewing a recommendation and reviewing the task's place in the plan are kept as separate concerns, exactly as their separate `POST` endpoints suggest.

### TASK-011 — Live Anthropic API Validation of the Mandatory Use Case

* **Task** — Close the "no live AI provider ever configured" gap named in `docs/FINAL_ENGINEERING_REPORT.md`'s Limitations by running the mandatory requirement — *"Build a scalable URL shortener service with APIs, persistence, and analytics."* — through the real Anthropic API end-to-end, rather than through `FakeAIProvider`.

* **AI First Attempt** — Analysis succeeded on the first live call (~24s round trip): 5 functional requirements, 1 non-functional requirement, 7 ambiguities (3 rated HIGH: analytics metrics undefined, API contract undefined, scale/latency targets undefined), 3 assumptions, 5 success criteria, 6 engineering concerns. * **Engineer Review** — The first failure (`-placeholder` suffix) is a plausible one-off AI formatting slip. * **Task** — Continue the same live-API session past task decomposition: review and accept `TASK-001` ("Design overall system architecture"), request AI design assistance, accept the recommendation, generate artifacts, and validate them.

* **AI First Attempt** — The DESIGN recommendation (AI-RUN-001, ~30s, `confidence: MEDIUM`) was genuinely strong: four-layer architecture (API/persistence/cache/async-analytics), a base62-counter-vs-hash-based short-code ADR with tradeoffs, and — unprompted — a risk entry explicitly noting that the task's own embedded "assumptions" text could be mistaken for instructions to the AI, and stating it was treated as context, not as a directive. * **Correction** — Raised `max_tokens` to 16384. Added `_unwrap_stringified_field()`: if schema validation fails, and exactly one top-level field of the raw tool-call input is a JSON string that itself decodes to a dict containing that same field (or to a list), retry validation against the unwrapped value before raising. Added `test_complete_structured_unwraps_a_stringified_json_field` and updated the token-budget regression test's floor to `>= 16384`.
